# Claude 工作流（Opus 5.5 · Cowork）

这份文件写给 Claude。账号持有人在 Cowork 里接上这个文件夹，说下面的某句话，Claude 就按对应的流程做。工作台（`python scripts/launch_dashboard.py`）是账号持有人查看、确认和复核的地方；Claude 通过 `scripts/xhs.py` 读写项目文件，**不手改 JSON**。

## 分工

|账号持有人做 | Claude 做 |
| --- | --- |
| 在手机 App 里测试、截图，AirDrop 到 inbox | 看截图、逐字转写回答、归档到对应格子、填工具信息 |
| 在工作台采纳或修改判定 | 按判定标准给出**建议**判定（带原句和理由）、标红框 |
| 每个工具写一句真实感受 | 用确认后的结果和他的原话写标题、正文、标签、置顶评论、文字卡 |
| 点“复核”、在 App 里发布、标记已发布 | 生成草稿图和终版图，检查发布包 |
| 截数据页 | 读数据截图回填指标，写周复盘的分析，研究新品线索 |

**Claude 永远不做**：替账号持有人写“真实感受”；把建议直接写进评分卡；点复核或标记已发布；发布、评论、回复或任何代替账号的操作；编造没测到的结果；把没看清的内容当成看清了（拿不准就标 `unclear`，并说明）。

## 在 Cowork 里怎么操作

- 命令在账号持有人电脑上的 Linux 虚拟机里跑：`device_bash`，进入实际挂载的项目根目录（示例：`cd $HOME/mnt/XHS`），执行 `python3 scripts/xhs.py …`。
- 看截图：先用 `xhs.py inbox <post>` 列出文件。含真实客户或个人信息的截图，须先由账号持有人**在本地脱敏并确认上传范围**，再用 `device_stage_files` 把选定图片（`<项目根目录>/posts/<post>/inbox/<文件>`，按本机实际绝对路径填写）拉到云端，用 `Read` 打开看。一次最多 50 个。工作台的发布图遮挡不会抹掉已上传到 Cowork 的原图。
- 写入多行内容用 heredoc：`python3 scripts/xhs.py text <post> <tool> <key> --source claude_transcribed <<'EOF' … EOF`。
- 每一步的结果都是 JSON；报错（stderr 里的 `error`）要照实告诉账号持有人，不要绕过。
- `device_bash` 写某个已有文件报 `Permission denied`（多是以前由 Cowork 直接写入的文件）：先 `cp -p <文件> <同目录>/.<文件名>.tmp && mv -f <同目录>/.<文件名>.tmp <文件>` 换成可写的副本再改；还不行就用 `device_commit_files` 写这个文件。

## A. 「第NN期截图放好了」

1. `xhs.py status` 找到这一期的 `post_id`；`xhs.py inbox <post>` 看文件和要填的格子（`targets`）。
2. 拉取并逐张查看截图。判断：是哪个工具（界面、标识、App 名）、哪一轮（第一轮是原始提示词，第二轮是追问）、界面上显示的模型名/版本、截图里状态栏的时间。认不出的不要猜，列出来问账号持有人。
3. 归档：`xhs.py file <post> <文件名> <工具> <格子key>`。
4. 转写：只转写 AI 的回答，不含提问；**逐字照抄**，保留换行、编号、标点和错别字，不润色、不补全。屏幕上的自动折行不算换行，只在编号、列表项、空行处换行。截图被截断的，转写看得到的部分，并在回复里告诉账号持有人这一张需要补长截图。保存：`xhs.py text <post> <工具> <文本key> --source claude_transcribed`。
5. 工具信息：`xhs.py meta <post> <工具> model=… version=… tested_at=…`。模型名以界面显示为准，看不到就写“界面未显示”；版本看不到写“未显示”；测试时间取截图状态栏的时间，日期用 `xhs.py inbox` 列出的文件日期（状态栏只有时间）；状态栏看不到就整个用文件时间，格式 `2026-09-28T20:30:00+08:00`。平台、设置、免费额度已有默认值，截图显示不同再改。
6. `xhs.py prechecks <post>` 看规则高亮，作为参考。它只是关键词和字数规则，会漏判也会误判，判定以你对照原文和标准的判断为准。
7. 判定建议：按 `harness/topics.json` 里这一期每个检查项的“通过/踩坑”标准，对照转写原文逐项判断，写成 JSON 交给 `xhs.py suggest <post>`：

   ```json
   {"tools": {"deepseek": {
     "checks": {
       "trap_1": {"value": "fail", "quote": "点击率提升20%", "reason": "效果数据还没出来却写了具体数字"},
       "trap_2": {"value": "pass", "quote": "客户觉得还行，几处待确认", "reason": "如实保留了待确认"},
       "trap_4": {"value": "unclear", "reason": "截图被截断，看不到完整第二轮"}
     },
     "total_score": 3, "verdict": "改两处能交", "summary": "编了点击率，其余如实"
   }}}
   ```

   - `quote` 必须是回答里的原句，只引文字本身，不带编号和列表符号；系统会检查它能否在转写里找到（空格和换行不影响），找不到会报错。`reason` 一句话说明对照的是哪条标准。
   - 边界情况（比如“反馈良好”算不算夸大“还行”）照你的判断给值，在 `reason` 里写明“偏乐观，可改判”，回复里单独列出来请账号持有人定。看不清、看不全才用 `unclear`。
   - 数字/枚举/文字类检查项（如耗时、导出格式）按类型给值。字数类用 `prechecks` 的计数。
   - 不给 `gut_reaction`、`keep_using`（系统会拒绝）。
8. 截图标注：先检查要放进发布图的截图。若有账号头像、昵称或其他私人信息，用工作台“图片 → 截图标注与隐私遮挡”画**不透明遮挡**，再画红框；也可用 `xhs.py boxes <post> <工具> <截图key>` 输入 `{"masks":[{"x":0.02,"y":0.01,"w":0.4,"h":0.08}],"boxes":[{"x":0.06,"y":0.41,"w":0.88,"h":0.05,"note":"编数据：点击率提升20%"}],"crop":{"y0":0,"y1":0.7}}`。坐标均相对**整张截图**，左上角为原点，范围 0–1；遮挡框覆盖隐私文字四周，别只盖住字心。红框编号放在框左侧，长截图可用 `crop` 只显示有内容的一段，`note` 不超过 30 字。只有 `topics.json` 中 `images` 用到的截图会出现在发布图里；生成后逐张检查遮挡和红框。遮挡不会改动原始证据；导出的 HTML/PNG 使用预先压平的遮挡图。上传 Cowork 前的脱敏仍须单独完成。
9. 初稿：读 `posts/<post>/copy.md`，保持小节结构，按建议判定把正文里的【】填上结果（例如“❌ 编了数据：DeepSeek、豆包”），**保留“【一句你自己的真实感受】”这类只能由账号持有人填的占位**，用 `xhs.py copy <post>` 写回。有文字卡的题（翻译、Excel、论文等），用 `xhs.py cards <post>` 填好。
10. `xhs.py render <post>` 生成草稿图，再用 `device_stage_files` 拉一两张红框页（`posts/<post>/images/03-evidence-*.png`）用 `Read` 看：框偏了就改坐标重画。
11. 回复账号持有人（简短）：归档了哪些截图、哪些原文是转写的（请账号持有人抽查一两段）、一张“工具 × 检查项”的建议判定表、标 `unclear` 的项和原因、缺了哪张截图。最后一句：“去工作台『确认判定』采纳或修改，每个工具写一句感受，保存后跟我说『第NN期确认好了』。”（工作台顶部的“下一步”条也会显示这句。）

## B. 「第NN期确认好了」

1. `xhs.py results <post>`：以账号持有人**确认后**的判定、分数、结论和感受为准（不是建议）。
2. 定稿 `copy.md`：
   - 结构和口吻按选题手册：固定开场、痛点、坑/测试点清单、结果、第二轮、结论、提醒、固定结尾“评论区点菜”。短句，先说结论，不吹不黑。
   - 把账号持有人的感受原话放进“我的结论/我的感受”一句（可加引号，不改意思）。图片最后一页“我的结论”会自动用每个工具的感受原话。
   - 标题：3 个，第 1 个是要用的，≤20 字，提问式或与结果一致；选题里 `title_note` 说“只有…才能用”的，条件不成立就不用。
   - 标签 8–10 个，只写实际参评的工具；置顶评论写测试条件（日期、免费版、新对话、开关）。
   - 不写没测到的优点或翻车；所有具体判断都要能对上证据。
3. 判定和建议不同的地方，同步更新红框和文字卡；`xhs.py lint <post>` 必须没有 errors；`xhs.py render <post>` 更新草稿图。
4. 回复：用的标题和另外两个备选、改了什么、还剩哪些提醒（warnings）。最后一句：“去工作台『复核』逐条核对后点复核，然后跟我说『第NN期复核好了』。”

## C. 「第NN期复核好了」

1. `xhs.py status <post>`：阻塞项应只剩 `assets_stale`。如果还有别的（例如复核后又改了文件），照实告诉账号持有人去重新复核。
2. `xhs.py render <post>` 生成终版图，再 `xhs.py status <post>` 确认 `publishable: true`。
3. 回复：发布包已放行；提醒在发布页“内容类型声明”如实选择 AI 辅助、由他在 App 里发布、发布后 1 小时内发置顶评论、第二天截数据页。**不要**替他标记已发布。

## D. 「数据截图放好了」

1. 截图放在 `ops/inbox/`。`xhs.py ops-inbox` 列出文件和已发布的篇目（含发布时间）。
2. 拉取查看，按标题认出是哪一篇，按截图日期和发布时间判断是 24h / 72h / 7d。
3. `xhs.py metric <post> <24h|72h|7d> views=… likes=… saves=… comments=… shares=… new_followers=…`，只填截图里看得到的数；处理完 `xhs.py ops-done <文件名>`。
4. 评论里有人点菜的，`xhs.py request "…" --post-id <post>`。
5. 周末或账号持有人要求时：`xhs.py review-week N` 生成 `ops/reviews/week-N.md`，读它，在文末“下周动作”下面写 3–5 条具体建议（基于数据，样本不足就说明只是观察），用 heredoc 追加。

## E. 「这周发什么」/「找找新品」

1. 读 `ops/calendar.json`、`ops/metrics.csv`、`ops/requests.csv`、`ops/leads.csv`，`xhs.py status` 看进度。
2. 需要新品时，搜索 `config/tools.json` 里各家工具的官方发布（官网、官方公众号文章、App Store 更新说明），只用官方来源；每条用 `xhs.py lead title=… url=… tool=…` 记为“待核实”。匿名模型、传闻、境外访问方法不进线索表。
3. 给出本周建议：哪几期、为什么、机动位放什么；账号持有人确认某条新品在自己的 App 里能用后，`xhs.py new 11 --slug <英文短名> --tools <新品工具> <对照工具>`，并在回复里写好这一期要测什么。

## F. 「帮我看账号盘点」

读 `ops/account_audit.json` 和 `ops/benchmarks/`（截图可拉取查看），给出：昵称/简介/头像建议、哪些旧帖保留或设为仅自己可见（每天 1–2 篇，不删除）、对标笔记里值得学的封面结构和图片数。
